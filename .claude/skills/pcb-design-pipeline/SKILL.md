# Сквозная разработка платы: ТЗ → ЭРИ → схема → плата → документы → производство

Скилл фиксирует технологию, по которой впервые пройден полный путь на проекте DDS 47–51 МГц
(ревизии B → E; репозиторий `C:\Project\DDS`, метки `revB-baseline`, `revE-baseline`).
Его задача — чтобы следующий проект шёл тем же путём, без повторного изобретения и с теми же проверками.

Если нужно изменить уже сделанную ревизию — читай `../pcb-revision-eco/SKILL.md`.
Перед любой работой в существующем проекте выполни `git pull` и прочитай `README_RU.md` и `docs/design_notes.md` проекта: там текущее состояние и открытые пункты.

## Принципы (почему процесс устроен именно так)

1. **Единый источник истины.** Цепочка однонаправленная:
   `база компонентов + заданные соединения → генераторы → проект KiCad → документы`.
   Visio, Word, PDF, BOM, Gerber — производные. Руками их не правят: правка потеряется при следующей сборке,
   а расхождение между документами и платой — это брак, который находят в производстве.
2. **Эталон соединений и сверка.** Для каждой ревизии хранится «заданный нетлист» (`verification/expected_*.json`) и
   нетлист предыдущей ревизии. `netcompare.py` сравнивает цепи как множества пар (позиция, вывод), поэтому
   перерисовка не считается изменением, а любая случайная потеря связи — считается. Без этой сверки «схема совпадает» — это мнение, а не факт.
3. **Стабильные ключи.** Каждый элемент имеет ключ (в DDS — обозначение ревизии C), из которого получаются UUID
   (`kisch.suid`). Поэтому пересборка даёт тот же объект, а `refmap` переводит ключи в обозначения ГОСТ 2.710.
   Это то, что позволяет вести ревизии как продолжение, а не как новый проект.
4. **Два режима работы — и порог между ними.**
   - *Режим генератора:* схема и плата строятся скриптами заново (`build_all.sh`, `route_all.sh`). Быстро, воспроизводимо, но **затирает ручные правки**.
   - *Режим ручной доработки:* файлы KiCad правятся руками или точечными скриптами; разрешён только `make_outputs.sh`.
   Переход из первого во второй необратим без потери правок. Фиксируй момент перехода в `docs/design_notes.md` и в `git`-метке.
5. **Заполнители видны и блокируют выпуск.** Всё неподтверждённое (посадочное место без чертежа, генератор без паспорта)
   называется `*_PLACEHOLDER` / `*_UNVERIFIED`, ставится в DNP при необходимости и перечисляется в «Открытых пунктах».
   Пометка «ЧЕРНОВИК» на Э3 снимается только когда список пуст.
6. **У каждой фазы есть вход, выход и проверяемые ворота.** Не переходи к следующей фазе, пока ворота не пройдены командой
   (а не «вроде получилось»). Результат ворот пиши в отчёт о фазе: число компонентов, цепей, нарушений.

## Фазы

| # | Фаза | Результат | Ворота (проверяемые) |
|---|---|---|---|
| 0 | Подготовка среды и проекта | Каркас каталогов, `env.sh`, git | `kicad-cli --version`, `python -c "import pcbnew"` в Python KiCad |
| 1 | ТЗ и архитектура | Блок-схема, бюджеты (питание, тепло, частоты), список допущений | Каждое требование ТЗ → узел схемы (таблица трассировки) |
| 2 | Выбор ЭРИ | База компонентов `*_parts.py`, список открытых вопросов по ТУ | Для каждой позиции: тип, ТУ/код заказа, корпус, статус «подтверждено / заполнитель» |
| 3 | Символы и посадочные места | `lib/*.kicad_sym`, `lib/*.pretty` | Каждое посадочное место привязано к чертежу корпуса или помечено заполнителем |
| 4 | Схема (Э3) | Листы `.kicad_sch`, нетлист | ERC = 0; сверка с заданным нетлистом = IDENTICAL |
| 5 | Плата: контур, стек, правила, расстановка | `.kicad_pcb` без трасс | Все компоненты в контуре, нет пересечений courtyard |
| 6 | Разводка | Разведённая плата | DRC со сверкой схемы (`--schematic-parity`): 0 нарушений, 0 неразведённых, 0 расхождений |
| 7 | Документы | PDF, BOM, нетлист, Visio Э3, Word ПЭ3 | Число компонентов: схема = BOM = ПЭ3 = CPL (+DNP); обозначения и листаж в штампах совпадают |
| 8 | Выдача в производство | `gerber.zip`, BOM/CPL JLC, `README_JLC.md` | Просмотр Gerber, список открытых пунктов пуст или явно принят заказчиком |
| 9 | Фиксация | `git`-метка ревизии, запись в «История», уроки | Метка `rev<X>-baseline` поставлена после чистой сборки |

Подробности по фазам — в `references/`. Читай только то, что нужно на текущей фазе:

- Фазы 1–3 (ТЗ, ЭРИ, символы, посадочные места) → `references/part-selection.md`
- Фаза 4 (схема, ГОСТ-оформление, нетлист-эталон) → `references/schematic-gost.md`
- Фазы 5–6 (стек, правила, ВЧ, разводка, чистка) → `references/pcb-layout-routing.md`
- Фазы 7–8 (документы, JLCPCB, предвыпускной чек-лист) → `references/documents-outputs.md`
- Раскладка каталогов, что в `tools/` универсально, а что специфично для DDS → `references/project-layout.md`
- Грабли (SWIG, `pro_merge`, кодировки, Freerouting) → `references/gotchas.md`
- Накопленные уроки по проектам → `references/lessons-learned.md`

## Порядок действий в сессии

1. `git pull`; прочитать `README_RU.md`, `docs/design_notes.md`, список открытых пунктов.
2. Определить фазу и режим (генератор / ручной) из `design_notes.md`. Если режим не записан — выяснить по `git log` и спросить пользователя.
3. Для новой фазы прочитать соответствующий файл из `references/`.
4. Выполнять работу малыми шагами; после каждого шага запускать ворота фазы.
5. Результат ворот сообщать числами (компонентов, цепей, нарушений), а не словами «всё хорошо».
6. В конце: обновить `docs/design_notes.md` (состояние и открытые пункты), `README_RU.md` (история), закоммитить.
   Коммит и `git push` — только по просьбе пользователя.

## Новый проект: с чего начать

Универсальные модули DDS (`kisch.py`, `sheet.py`, `gost_symbols.py`, `gost_wks.py`, `netcompare.py`, `pro_merge.py`,
`minirouter.py`, `zero_len.py`, `drc_fix.py`, `silk_place.py`, `pcb_meta.py`, `jlc_bom_cpl.py`, `sch2vsdx.py`, `pe3_docx.py`, `env.sh`)
переносятся в новый проект как есть, но имя проекта `DDS_47_51` в них зашито (см. `references/project-layout.md`, раздел «Что параметризовать»).
Специфичны для изделия: `dds_build.py` (содержимое листов), `dds_parts.py`, `eco.py`, `dds_pcb.py` (расстановка, ВЧ-трассы), `make_footprints.py`.
Не копируй специфичные файлы механически — возьми их как образец структуры.

Если пользователь не требует ГОСТ-оформления (прототип, не для выпуска), фазы 7 и часть 4 упрощаются:
пропусти Visio/Word и рамку ГОСТ, но оставь нетлист-эталон, ERC/DRC и список открытых пунктов.

## Как улучшать этот скилл

Скилл должен расти вместе с проектами. После каждого проекта или ревизии:

1. Добавь в `references/lessons-learned.md` запись: что сломалось, почему, как нашли, какое правило теперь действует (формат — в самом файле).
2. Если урок — это проверка, которую можно автоматизировать, добавь её в ворота соответствующей фазы и в `tools/`.
3. Если шаг оказался лишним или вводил в заблуждение — удали его, а не оставляй «на всякий случай».
4. Если появился новый тип изделия (другая элементная база, другой производитель плат) — добавь отдельный файл в `references/`, а не раздувай `SKILL.md`.
