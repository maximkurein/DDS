# Проверка замечаний к прошивке DDS

Дата: 06.11.2026. Проверены исходники `firmware/` из коммита `40b6ebf`, версия 1.0.0, и первоначальные замечания. Актуализированный список сохранён в [REMARKS.md](../firmware/REMARKS.md); ниже объясняется, какие утверждения исходного разбора потребовали уточнения. Это статический разбор: повторная сборка, симуляция и аппаратные испытания не выполнялись. Исходники прошивки этим документом не изменяются.

## Результат по четырём замечаниям

| № | Вывод | Основание |
|---|---|---|
| 1 | Поведение подтверждено; способ исправления нужно уточнить | `pl8t_check_alive()` сравнивает всё слово CTR с `s_ctr`; `fault()` выключает DDS, после чего следует пауза 500 мс и новый запуск |
| 2 | Ошибка обработки накопленных тиков подтверждена | `sample_inputs(ticks)` читает вход один раз, затем многократно передаёт этот уровень в `debounce_update()` |
| 3 | Нужна калибровка, но объяснение про обязательные 1 МГц неверно | CKSEL выбирает номинальный диапазон RC, OSCCAL корректирует его. Отсутствие пары байтов EEPROM не переключает CKSEL |
| 4 | Проверка PGOOD только в RUN подтверждена; программная защита имеет дополнительные ограничения | В RESET/RECOVER нет общего выхода по потере питания; `pl8t_init()` блокирует опрос приложения на время SPI |

## 1. Проверка CTR

Несовпадение действительно вызывает отключение даже после одного ошибочного чтения. Длительность отсутствия сигнала больше самой паузы 500 мс: добавляется повторная инициализация. Наличие самостоятельно меняющихся флагов CTR исходным замечанием не доказано; это нужно проверять по таблице регистра, а не предполагать по аналогии с SEL_REG.

Перед исправлением определить маску значимых битов по ТО. Учитывать и биты, которые прошивка намеренно держит в нуле: например, отключение второго ЦАП и компаратора. Маска только `DAC1_ON | cmx` может пропустить нежелательное включение других функций.

Повторное чтение может отделить единичный сбой от устойчивого. Требование именно двух **одинаковых** неправильных слов недостаточно: чередующиеся ошибки тоже должны приводить к ограниченному по времени отказу. Нужна политика с конечным числом повторов и проверкой на модели SPI.

## 2. Накопленные тики и дребезг

Счётчик времени не хранит историю входного уровня. Например, 25 накопленных тиков и один низкий замер PGOOD сейчас дают 25 одинаковых образцов, хотя низкий уровень мог появиться непосредственно перед чтением.

Минимальное улучшение — не считать один замер несколькими независимыми образцами. Однако просто один вызов `debounce_update()` на опрос тоже не доказывает непрерывную устойчивость за весь длительный пропуск. При реализации выбрать явную стратегию: периодическое семплирование либо сброс подтверждения после слишком длинного интервала. Проверить короткие импульсы после паузы и длительное устойчивое изменение. Тесты только функции `debounce_update()` не покрывают способ её вызова из приложения.

## 3. CKSEL и OSCCAL — разные настройки

В [ТО 1887ВЕ7Т](<../info/1887BE1T/Руководства по эксплуатации/ТО 1887ВЕ7Т.pdf>), раздел 3.3.7, таблица 3.13 (стр. 53), CKSEL=`0001` задаёт номинальные 1 МГц, CKSEL=`0100` — 8 МГц. На стр. 300 указана автоматическая загрузка калибровки **для 1 МГц** при сбросе и необходимость программно загрузить соответствующий байт для другого диапазона.

Если уже записан Low fuse `0x24`, отсутствие калибровки 8 МГц означает неподходящую коррекцию выбранного диапазона, а не гарантированную частоту ядра 1 МГц. Поэтому нельзя автоматически пересчитать UBRR на 1 МГц только по `OSCCAL_MISSING` и нельзя утверждать, что SPI обязательно замедлится ровно в восемь раз.

Практический порядок из замечания полезен: фьюзы → индивидуальная калибровка → прошивка → проверка UART. Сообщение `factory 1 MHz` в `main.c` стоит заменить при следующей правке кода на формулировку об отсутствующей калибровке 8 МГц. В USER_GUIDE смысл текущей строки объяснён без изменения прошивки.

## 4. Контроль питания во время запуска

Общий контроль PGOOD нужен и до RUN. Но проверка на входе в INIT не прерывает уже начатую блокирующую `pl8t_init()`: для ограничения этого окна потребуется проверять питание между этапами обмена или сделать инициализацию пошаговой.

`dds_shutdown()` задаёт RESET и отключает выходы D3 через OE#. Оно не переводит все 5-вольтовые выходы МК в высокоимпедансное состояние. Следовательно, одно это изменение не доказывает отсутствие подпитки через входные защиты при пропавших +3,3 В. Электрическое поведение D3, резисторов и линии PC4 проверяется отдельно; +1,8 В программой вообще не контролируется.

## Что учтено в руководстве

- Порядок Probe → Backup → Read fuses → Debug fuses → OSCCAL → Flash → UART.
- Режим ATmega103 при начальном E=`0xFD` и целевой E=`0xFF` для текущей программы.
- RX адаптера на X1.1, земля X1.6, вход 5 В, параметры 38400 8N1.
- Различие между восстановлением DDS с сохранением ОЗУ МК и полным сбросом МК: частота в EEPROM не сохраняется.
- DEVID-ошибка не определяет однозначно отсутствие такта, а значение амплитуды 4095 не подтверждает уровень −10 дБм.
- Статусы аппаратных проверок: размер страницы flash, DEVID, ВЧ-выход, питание и avarice остаются открытыми.

Исправление пунктов 1, 2 и 4 потребует изменения кода и дополнительных сценариев тестирования. В этом проходе подготовлены документы, а не новая версия прошивки.
